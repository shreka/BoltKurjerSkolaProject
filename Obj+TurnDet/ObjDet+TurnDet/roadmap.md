# Roadmap: робот-курьер (школа)

Стек: Arduino Uno + BLE, Android (Java, Android Studio) — центральное apk,
Python-модули (объезд препятствий ИИ, навигация/повороты) работают отдельным
процессом в Termux на том же телефоне, связь с Java — локальный
socket/HTTP на 127.0.0.1.

Статус на старте:
- BLE-связь Arduino↔телефон физически работает, протокол команд/одометрии не написан
- Энкодеров на моторах нет (нужно купить/поставить)
- Карта школы не спроектирована
- ИИ объезда препятствий — в разработке
- turn_and_clearance_detector.py — готов (базовая версия)

Правило: делать по одному route (1-2 поворота) до конца пайплайна, потом
расширять. Не пытаться сразу собрать всю школу.

---

## Phase 0 — Железо
- [ ] Купить энкодеры для TT-моторов (диск + ИК-вилка) или TT-моторы со
      встроенным энкодером — 2 шт (по одному на ведущее колесо)
- [ ] Подтвердить модель драйвера моторов (L298N / TB6612 / др.)
- [ ] Зафиксировать положение камеры телефона на корпусе (угол, высота) —
      от этого зависят калибровки в turn_and_clearance_detector.py

## Phase 1 — Протокол BLE (сделать ДО прошивки и ДО Java-кода)
- [ ] Phone → Arduino: команды, например `CMD:FWD`, `CMD:LEFT90`,
      `CMD:RIGHT90`, `CMD:STOP`
- [ ] Arduino → Phone: одометрия, например `ODO:<tick_count>` каждые N мс
      или при изменении
- [ ] Формат: простые ASCII-строки в BLE characteristic (проще всего
      дебажить через nRF Connect)
- [ ] Зафиксировать протокол в отдельном файле `ble_protocol.md` (таблица
      команда → действие)

## Phase 2 — Прошивка Arduino
- [ ] Подключить энкодеры на пины с прерываниями (interrupt), написать
      счётчик тиков
- [ ] Примитивы движения: forward(), turn_left_90(), turn_right_90(), stop()
- [ ] Протестировать примитивы БЕЗ BLE (захардкоженная последовательность)
- [ ] Подключить BLE: приём команд из Phase 1, периодическая отправка
      тиков одометрии
- [ ] Тест: слать команды вручную через nRF Connect, проверить
      движение + приход одометрии

## Phase 3 — Карта школы (с нуля)
- [ ] Нарисовать граф коридоров на бумаге: узлы = перекрёстки, рёбра =
      прямые участки
- [ ] Для каждого перекрёстка: какие направления реально существуют
      (Left/Forward/Right) + примерная дистанция в тиках от предыдущего узла
- [ ] Для каждого кабинета: к какому перекрёстку привязан + способ
      подтверждения (пока — просто "последний поворот + фиксированная
      дистанция", распознавание номера двери — отдельная задача потом)
- [ ] Сохранить как простой JSON, читаемый Python-навигатором:
      `{nodes: [...], edges: [...], turns: {...}}`
- [ ] Выбрать ОДИН тестовый маршрут (1-2 поворота) для первого прогона

## Phase 4 — Python: навигация (turn_and_clearance_detector.py)
- [x] Базовая версия готова
- [ ] Прикрутить реальные пороги тиков из Phase 3 (min_distance_ticks и
      расстояния между узлами)
- [ ] Откалибровать OPEN_DENSITY_MAX / WALL_DENSITY_MIN / MIN_TEXTURE_STD
      на реальных фото школьных коридоров (не квартиры)
- [ ] Обернуть в простой локальный сервер (Flask/FastAPI или голый
      socket) внутри Termux: принимает кадр + тики, отдаёт результат в JSON

## Phase 5 — Python: объезд препятствий (параллельная разработка)
- [ ] Завершить текущий ИИ-модуль (opencv/ultralytics — ставятся в
      Termux через обычный pip, без ограничений Android ABI)
- [ ] Зафиксировать контракт вывода, например:
      `{"obstacle": bool, "clear_side": "left" | "right" | None}`
- [ ] Добавить в тот же локальный сервер Termux ещё один эндпоинт/поток
      (см. Phase 4) — держать в уме: этот модуль работает непрерывно в
      фоне, модуль поворотов — только по требованию, чтобы не
      перегружать Huawei P Smart 2019

## Phase 6 — Termux + Android (Java) — оркестратор
- [ ] Установить Termux на телефон, поставить Python + opencv +
      ultralytics через pip (обычный pip, без сборки под Android ABI)
- [ ] Поднять локальный сервер в Termux на 127.0.0.1:PORT (Flask/FastAPI
      или голый socket) — принимает кадры/тики, отдаёт JSON-результаты
      обоих Python-модулей (Phase 4, Phase 5)
- [ ] Настроить автозапуск Python-сервера в Termux при старте телефона
      (termux-boot или ручной запуск перед выездом робота — зависит от
      того, насколько автономным должен быть запуск)
- [ ] Java-apk: BLE central — подключение к Arduino, чтение/запись
      characteristics по протоколу Phase 1
- [ ] Java-apk: камера (CameraX/Camera2), кадры отправляются на
      localhost-сервер Termux по HTTP/socket, результат — обратно в JSON
- [ ] Главный цикл оркестратора (Java):
      - постоянно: кадр → запрос к серверу Termux (объезд препятствий)
      - постоянно: чтение одометрии из BLE
      - при приближении к узлу карты (по тикам) → запрос проверки
        поворота (Phase 4) на несколько кадров
      - собрать финальную команду → отправить по BLE
- [ ] Логирование: тики / CV-результаты / отправленные команды — в файл,
      для разбора полётов после тестов

## Phase 7 — Стендовый тест (без реальной езды)
- [ ] Проверить, что Java-apk достучится до localhost-сервера Termux
      (простой ping/echo эндпоинт)
- [ ] Подать в оркестратор тестовые фото + фиктивные значения тиков,
      проверить, что логика выбирает правильное действие
- [ ] Проверить BLE round-trip: команда отправлена → мотор среагировал →
      пришла одометрия

## Phase 8 — Полевой тест (один маршрут)
- [ ] Только тестовый маршрут из Phase 3 (1-2 поворота)
- [ ] Логировать всё, разобрать сбои, поправить пороги/дистанции
- [ ] Только после стабильной работы — расширять карту

## Phase 9 — Итерации
- [ ] Пауза счётчика тиков во время манёвра объезда препятствий
      (обсуждали ранее — событие start/stop манёвра от модуля объезда)
- [ ] Подтверждение прибытия в нужный кабинет (номер двери OCR или
      фиксированная дистанция) — отдельный небольшой модуль
- [ ] Постепенно расширять карту / маршруты, каждый раз — новый цикл
      Phase 7 → Phase 8 для нового участка
